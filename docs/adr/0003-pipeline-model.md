# ADR-0003. Модель пайплайна

Статус: принято, 2026-11-10.

**Решение.** Упорядоченные стадии. Стадия — один `step`, `parallel` (≥ 2 шагов) или `foreach` (шаг на элемент CEL-списка, `max_parallel`). Fan-in задаётся `join` (`all`, `any`, `quorum`) со стратегией `merge`. Условия `when` и переходы `routes` описываются на CEL. Обратный переход обязан иметь `max_visits`, при превышении run уходит в `needs_attention`. Надёжность: `timeout`, `lease` (heartbeat) и `retry` с backoff, настраиваются на шаге или через `defaults`.

**Почему не произвольный DAG.** Позиция на конвейере нужна для 3D-вида и для понимания. Стадии с параллельными дорожками покрывают видео, гео и Hello World. Циклы явны и ограничены.

**Дополнение (contract 0.3.0).** Ожидание человека — не долгий шаг, а `wait` + `step.waiting` с `on_timeout` (ADR-0014). Заход в стадию по `routes` — новый визит с собственным `step_key`; история визитов доступна в CEL (ADR-0012). `max_visits` считается на стадию-цель. Admission упорядочен по `priority`, `concurrency.min_interval` ограничивает частоту стартов, `budget` — расход.

**Последствия.** Run закреплён за ревизией пайплайна. Каждая попытка хранит полный неизменяемый запрос, поэтому retry и resume отправляют то же самое (закрывает проблемы v1 #2–#6).
